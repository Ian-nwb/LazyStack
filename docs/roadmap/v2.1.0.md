## B. Hosting planner

Goal: help the user decide **what kind of hosting** each app needs. The default is **local**: the project just runs on your machine and isn't deployed. The planner then covers every common option: static/CDN, serverless, BaaS, PaaS, self-hosted PaaS, managed containers, Kubernetes, cloud VM, VPS and dedicated/bare metal and show example services for that kind. It is advice only. It must not generate new deploy files or change existing Compose/Terraform/K8s output, but it should point to the files LazyStack already generates for each type (Compose, `fly.toml`, `render.yaml`, K8s manifests/Helm, Terraform for AWS/GCP/DigitalOcean). Follow the existing code style and the layered patterns already in the repo.

### B1. Types and data
- `src/types.ts`: `export type HostingType = 'local' | 'static' | 'serverless' | 'baas' | 'paas' | 'self-hosted-paas' | 'containers' | 'kubernetes' | 'cloud-vm' | 'vps' | 'bare-metal'`. Add an optional `hosting?: HostingType` to `CartApp`: it's the user's choice, and absent means `local` (the default: running on this machine only, not deployed). The suggestion is still computed and shown as "when you deploy" advice. Because it's optional, blueprints without it stay valid. Teach the blueprint validator to accept it and reject unknown values.
- `src/data/hosting.ts`: one entry per `HostingType` with `label`, `summary`, `goodFor[]`, `watchOutFor[]`, `examples[]` (plain names, no prices), `upkeep: 'none' | 'low' | 'medium' | 'high'`, and `generatedFiles[]` (which LazyStack outputs apply, if any). Use this content (plus `local`: label "Local only", summary "Runs on your machine with the generated dev orchestrator and Compose files; not deployed", good for development, demos, personal and LAN-only tools, watch out for "Not reachable from the internet; stops when your machine does", examples Docker Compose, `lazystack dev`, upkeep none, files Compose, dev orchestrator, `.env`):

| Type | Summary | Good for | Watch out for | Examples | Upkeep | LazyStack files |
|---|---|---|---|---|---|---|
| static | Built files served from a global CDN, no server | SPAs, docs, marketing sites, static Astro/SvelteKit/Vite builds | Can't run server code; APIs live elsewhere | Cloudflare Pages, Netlify, GitHub Pages, S3 + CloudFront | none | – |
| serverless | Functions per request, scale to zero | SSR apps, light APIs, webhooks, spiky or low traffic | Cold starts, time limits, no long-lived connections, usage-based bills | Cloudflare Workers, Vercel, Netlify Functions, AWS Lambda, Google Cloud Functions, Azure Functions | none | – |
| baas | A hosted backend (auth, database, storage, functions) you call from the client | Apps whose backend is mostly CRUD + auth; mobile and frontend-only teams | Lock-in to the provider's APIs; custom logic squeezed into their functions | Supabase, Firebase, Appwrite Cloud, PocketBase (hosted), Convex | none | cloud service clients + env vars |
| paas | Push code or a Dockerfile; the platform runs and scales it | Full-stack apps, APIs with a database, getting started fast | Always-on services bill when idle; managed databases cost extra | Railway, Render, Fly.io, Heroku, DigitalOcean App Platform, Koyeb | low | `fly.toml`, `render.yaml` |
| self-hosted-paas | PaaS-style git-push deploys running on your own server | Heroku-like workflow at VPS prices, many small apps on one box | You still own the server underneath | Coolify, Dokku, CapRover, Kamal | medium | Compose, Dockerfiles |
| containers | Your Docker image on a managed runtime, no cluster to run | Docker apps, polyglot stacks, scale-to-zero containers | More config than a PaaS | Google Cloud Run, AWS App Runner, AWS ECS Fargate, Azure Container Apps | low | Dockerfiles, Terraform (AWS ECS) |
| kubernetes | Managed cluster running your containers | Many services, autoscaling, teams already on K8s | Steep learning curve, cluster cost even when idle | GKE, EKS, AKS, DigitalOcean Kubernetes, Linode LKE | high | K8s manifests, Helm chart |
| cloud-vm | A virtual machine from a hyperscaler, inside its network and IAM | Workloads that need the rest of AWS/GCP/Azure (private networking, managed DBs, IAM), compliance, reserved/spot pricing | Pricier than a VPS for the same size; egress and extras billed separately; you manage the OS | AWS EC2, Google Compute Engine, Azure Virtual Machines, Oracle Cloud | high | Terraform (AWS/GCP/DO), Compose, GitHub Actions SSH deploy |
| vps | A simple virtual server at a flat monthly price | Lowest steady cost, full control, whole stack + DB on one box via Compose | You handle updates, backups, TLS, monitoring | Hetzner, DigitalOcean Droplets, Linode, Vultr, AWS Lightsail | high | Compose, proxy config, GitHub Actions SSH deploy |
| bare-metal | A dedicated physical server (rented or your own/on-prem) | Heavy steady load, GPUs, data that must stay on your hardware | Hardware failures, no instant scaling, most upkeep of all | Hetzner dedicated, OVHcloud, Latitude.sh, your own homelab or on-prem servers | high | Compose, proxy config |

Also export a one-line "VPS vs cloud VM" note (a VPS is a flat-priced box from a simple host; a cloud VM lives inside AWS/GCP/Azure with their networking, IAM and managed services, and bills per resource), and a short "before you pick" list: free tiers can be personal-use only or go offline when credits run out; usage billing can overshoot, so set alerts or caps; databases are usually a separate bill; cloud VMs and hyperscaler services charge for egress; PaaS/serverless/BaaS manage servers for you, while VPS, cloud VM and bare metal are yours to maintain. Prices change, so check the provider's pricing page.

### B2. Rules (pure function, unit-tested)
`src/utils/hostingPlanner.ts`:
- `suggestHosting(app: CartApp, tech: TechItem, settings: ProjectSettings): { type: HostingType | null; reasons: string[] }`
- `planHosting(settings)`: returns per-app results (suggestion, the override if set, and the effective type) plus a list of alternatives per app (the other types that would also work, each with a one-line why), and stack-level notes: "Whole stack on one bill: a VPS (or Coolify/Dokku on it) with the generated Compose files" when there's more than one app or any Compose database; "Kubernetes fits: Helm chart and manifests are already generated" when there are 4+ server apps; "Already on AWS/GCP/Azure? Use a cloud VM or their container service with the generated Terraform" always as the last note.

Rules, in priority order (the first match wins, and each pushes a human-readable reason):
1. `tech.hostOnly` or role `desktop-mobile` → `type: null` ("Runs on the user's device; not hosted").
2. role `static-site`, or a frontend whose tech builds to static files (SPA/Vite/static generators; add a `staticOutput?: boolean` to the relevant `TechItem`s in `src/data/frameworks.ts` rather than matching on names) → `static`. If the stack's only backend is a BaaS cloud service (Supabase, Firebase, Appwrite, PocketBase…), add the alternative `baas` for the backend part.
3. role `worker`, or the app connects to a broker/queue/realtime service (Kafka, NATS, RabbitMQ, Redis pub/sub, etc. via `connections`/databases) → `paas` ("Needs an always-on process; serverless functions sleep and time out"). Alternatives: `containers`, `vps`, `cloud-vm`.
4. role `fullstack` or SSR frontend whose tech supports serverless/edge (add `serverlessAdapter?: boolean` on `TechItem`: Next.js, Nuxt, SvelteKit, Astro, Remix, Hono, etc.) → `serverless`; otherwise → `paas`. Alternatives: `containers`, `self-hosted-paas`.
5. role `backend` connected to a database → `paas` ("Easiest path for an API + database"). Alternatives: `vps` ("cheapest: DB on the same box"), `cloud-vm` ("if you need managed DBs/IAM from a hyperscaler"), `containers`.
6. Any app that is Docker-only or uses a runtime without serverless support → `containers`. Alternatives: `paas`, `kubernetes`, `vps`.
7. Fallback → `paas`.

`bare-metal`, `kubernetes`, `cloud-vm`, `self-hosted-paas` and `baas` are never the first suggestion on their own except where listed above; they appear as alternatives and as manual override choices, so the user can always pick any of the ten deploy types, or stay on `local`.

Add cases to `scripts/unit-tests.ts` covering each rule, the alternatives lists, every one of the eleven types (including `local`) accepted, the choice taking precedence over the suggestion, and a blueprint with no `hosting` fields resolving to `local` with the suggestion still reported.
