## 2. Port-conflict check before scaffolding

Today the generator validates folder names, paths, connection env-var names, health checks and dependency cycles, but nothing checks ports. Two services on the same host port, or a port already taken on the machine, only shows up when `docker compose up` or the dev orchestrator fails.

### Checks

1. **Internal duplicates (always, pure):** every host-published port across apps, databases, DB admin UIs, the proxy and broker management UIs must be unique. Report both owners, e.g. `Port 8080 is used by "api" and "pgadmin"`.
2. **Machine conflicts (warn only, needs a socket probe):** try to bind each host port on `127.0.0.1` / `0.0.0.0` and report ports already in use, with the owning process when it can be found (`ss -ltnp` on Linux, `lsof` on macOS, `netstat -ano` on Windows).
3. **Reserved ports:** warn on privileged ports (< 1024) for non-proxy services, and on ports commonly claimed by the OS.
4. **Suggest a fix:** propose the next free port in the same range and let the user accept it.

### Where it lives

- Internal check in `scaffoldProject`'s validation step next to the other checks, so the CLI, Electron and Vite middleware all get it. It returns `{ success: false, error }` like the others.
- Machine probe in a new `electron/environment/ports.ts` (beside `auditor.ts`), exposed through IPC `check-ports`, a Vite `/api/ports` middleware (CLAUDE.md requires keeping both in sync) and a CLI command: `lazystack ports --config <file>`; `scaffold` runs it unless `--skip-port-check` is passed.
- UI: show conflicts inline on the offending app or database card and in the pre-scaffold summary; auto-fix button applies the suggested port.
- Augment mode: ignore ports already owned by the project's own running stack, and only check the newly added services.
- Dry run reports conflicts as warnings, not failures.

### Decisions

- Internal duplicate ports **block** scaffolding.
- Machine port conflicts **warn only** and never block, since the stack may not be started right away.
- The internal duplicate check runs **live** while editing the blueprint; the machine probe runs on demand and at scaffold time.

## 3. Message brokers and caches as first-class picks

Findings from the catalog:

- `redis`, `valkey`, `rabbitmq` and `kafka` already exist, but inside `DATABASE_CATALOG` (`src/data/databases.ts`) with `category: 'message-broker'` or `'key-value'`. They are treated as databases: they appear in the database picker and get a Compose service and credentials, but no dedicated UI, role or wiring.
- NATS is missing.

### Scope

| ID | Name | Status | Compose image | Ports |
| --- | --- | --- | --- | --- |
| `redis` | Redis | exists | `redis:7.2-alpine` | 6379 |
| `valkey` | Valkey | exists | existing | 6379 |
| `rabbitmq` | RabbitMQ | exists | `rabbitmq:3-management-alpine` | 5672, 15672 (UI) |
| `kafka` | Apache Kafka (KRaft) | exists | `apache/kafka` | 9092 |
| `nats` | NATS (JetStream) | **new** | `nats:2` with `-js` | 4222, 8222 (monitoring) |

Possible follow-ups once the pattern works: Redpanda (Kafka API), Mosquitto (MQTT), ElasticMQ (SQS-compatible).

### Work

- **Own section in the picker:** a "Messaging and caching" group separate from databases. Keep the same data model (`SelectedDatabase`) unless an app-level concept is needed, to avoid breaking blueprints; change the UI grouping and add `category` values (`cache`, `message-broker`) only.
- **Connection wiring:** when an app connects to a broker or cache, generate the env vars and a per-language client snippet:
  - `REDIS_URL`, `RABBITMQ_URL` (amqp), `KAFKA_BROKERS`, `NATS_URL`, with the right in-network hostname for Docker apps and `localhost:<published port>` for host-run apps.
  - Starter-file client modules per ecosystem (Node, Python, Go, Rust, JVM, .NET), following how `cloudServices.ts` emits SDK clients for BaaS. One connect/publish/subscribe example each, behind the app's health check.
  - Add the broker to the app's `depends_on` with a healthcheck condition (`redis-cli ping`, `rabbitmq-diagnostics check_running`, NATS `/healthz`).
- **Dev orchestrator:** start brokers first and wait for readiness before launching host-run apps that depend on them.
- **Credentials:** generate broker passwords into `.env` the same way database credentials are created in `templates/meta.ts`.
- **Admin UIs:** extend `databaseAdminUis.ts` (Redis Commander already exists) with Kafka UI and a NATS dashboard option; RabbitMQ's management UI is built in.
- **Importer:** detect these images in Compose files in `electron/project/importer.ts`, including `nats`.
- **Docs:** update `docs/framework-layouts.md` and the README feature list.

### Verification

- `npm run verify:templates` and `npx tsc --noEmit`.
- Scaffold a stack with each broker and one app per ecosystem, then `docker compose config`; for Redis and NATS also bring the stack up in CI and run the generated connect example.
- Import round-trip recognizes the brokers.
- The port check from section 1 covers the broker ports and management UIs.

## 4. Suggested order

Group into small releases or PRs so `verify:templates` failures stay easy to trace:

1. Node/JS frontends and backends (1a, 1b) share the Vite/Node Dockerfile and `javascript.ts` plumbing.
2. Python (1c) all go in `native/python.ts`.
3. Static site generators (1d). They need a build-then-serve Dockerfile pattern that does not exist yet; add it once and reuse it.
4. Other languages (1e), each with its own ecosystem module and toolchain `requires` entry.
5. Port-conflict check (section 2). Land it before the brokers so the new broker ports are covered from the start.
6. Brokers and caches (section 3).

- Static site generators get their own `static-site` role.
